# cresclab-netcheck

[English](README.md) · [繁體中文](README.zh-TW.md) · [日本語](README.ja.md) · ไทย

> เอกสารนี้แปลจาก [README.md](README.md) หากเนื้อหาไม่ตรงกัน ให้ยึดฉบับภาษาอังกฤษเป็นหลัก

เครื่องมือวินิจฉัยเครือข่ายสำหรับลูกค้าที่เชื่อมต่อบริการของ Crescendo Lab เช่น MAAC และ CAAC ไม่ได้ ลูกค้ารันโปรแกรมหนึ่งตัวบนคอมพิวเตอร์และเครือข่ายที่มีปัญหา แล้วส่งรายงานที่เป็นไฟล์ข้อความกลับมา รายงานจะบอกว่าการเชื่อมต่อล้มเหลวที่จุดใด ได้แก่ DNS, TCP, TLS, HTTP, ไฟร์วอลล์ที่กรองตามชื่อโดเมน, ข้อจำกัดขนาดแพ็กเก็ต หรือเส้นทางเครือข่าย

เครื่องมือนี้อ่านข้อมูลเท่านั้น และไม่เปลี่ยนแปลงการตั้งค่าใด ๆ

## ดาวน์โหลด

ดาวน์โหลดจาก[เวอร์ชันล่าสุด](https://github.com/chatbotgang/cresclab-netcheck/releases/latest) repository นี้เป็นแบบ private จึงเปิดหน้า release ได้เฉพาะสมาชิกขององค์กร chatbotgang ให้ดาวน์โหลดไฟล์แล้วส่งให้ลูกค้าพร้อมกับ[คู่มือสำหรับลูกค้า](docs/customer-guide.zh-TW.md) (ภาษาจีนตัวเต็ม)

แต่ละเวอร์ชันมีไฟล์บีบอัดสำหรับแต่ละแพลตฟอร์ม, ไฟล์ `cresclab-netcheck.bat` แยกต่างหาก และ `checksums.txt` ชื่อไฟล์บีบอัดอยู่ในรูปแบบ `cresclab-netcheck_<เวอร์ชัน>_<ระบบปฏิบัติการ>_<สถาปัตยกรรม>` ให้เลือกจากส่วนท้ายของชื่อไฟล์

### วิธีเลือกไฟล์

| คอมพิวเตอร์ | ชื่อไฟล์ลงท้ายด้วย | บิลด์ | รันจริงใน CI |
| --- | --- | --- | --- |
| Windows ที่ใช้ Intel หรือ AMD (คอมพิวเตอร์ส่วนใหญ่) | `_windows_amd64.zip` | ✓ | ✓ เครือข่ายปกติและเครือข่ายที่ถูกบล็อก |
| Windows ที่ใช้ Arm เช่น โน้ตบุ๊ก Snapdragon | `_windows_arm64.zip` | ✓ | — |
| Mac ที่ใช้ชิป Apple (ซีรีส์ M) | `_darwin_arm64.tar.gz` | ✓ | ✓ |
| Mac ที่ใช้โปรเซสเซอร์ Intel | `_darwin_amd64.tar.gz` | ✓ | — |
| Linux ที่ใช้ Intel หรือ AMD | `_linux_amd64.tar.gz` | ✓ | ✓ |
| Linux ที่ใช้ Arm | `_linux_arm64.tar.gz` | ✓ | — |

`amd64` หมายถึงโปรเซสเซอร์ Intel หรือ AMD แบบ 64 บิต (เรียกอีกอย่างว่า x64 หรือ x86-64) ส่วน `arm64` หมายถึงโปรเซสเซอร์ Arm แบบ 64 บิต

- **Windows:** กด Windows+R พิมพ์ `ms-settings:about` แล้วดูข้อมูลโปรเซสเซอร์ใต้ **ข้อมูลจําเพาะของอุปกรณ์** หากมี `x64` ให้เลือก `windows_amd64` หากมี `ARM` ให้เลือก `windows_arm64` หรือรัน `$env:PROCESSOR_ARCHITECTURE` ใน PowerShell ซึ่งจะแสดง `AMD64` หรือ `ARM64` หากไม่แน่ใจ ให้เลือก `windows_amd64` เพราะ Windows 11 on Arm รันโปรแกรม x64 ได้ผ่านการจำลอง
- **macOS:** เลือก **เมนู Apple** > **เกี่ยวกับ Mac เครื่องนี้** หากแสดง **ชิป** ตามด้วยชิป Apple M ให้เลือก `darwin_arm64` หากแสดง **โปรเซสเซอร์** ตามด้วยโปรเซสเซอร์ Intel ให้เลือก `darwin_amd64`
- **Linux:** `uname -m` แสดง `x86_64` ให้เลือก `linux_amd64` และแสดง `aarch64` หรือ `arm64` ให้เลือก `linux_arm64`

ไฟล์บีบอัดสำหรับ Windows มี `cresclab-netcheck.bat` ด้วย ซึ่งเป็นเวอร์ชันข้อความธรรมดาที่ทีม IT ของลูกค้าเปิดอ่านได้ก่อนรัน หากนโยบายของบริษัทบล็อกไฟล์ปฏิบัติการที่ไม่มีลายเซ็น ให้ใช้ไฟล์นี้แทน ส่วน `.exe` ทำงานเร็วกว่าและมีส่วนสรุปเพิ่มเติม

### วิธีเปิดโปรแกรมเมื่อระบบบล็อก

ไฟล์ปฏิบัติการไม่มีการเซ็นโค้ด ดังนั้นเมื่อรันไฟล์ที่ดาวน์โหลดมาเป็นครั้งแรก Windows และ macOS จะแสดงคำเตือน

**Windows:** เมื่อหน้าต่าง **Windows protected your PC** ปรากฏขึ้น ให้คลิก **ข้อมูลเพิ่มเติม (More info)** แล้วคลิก **เรียกใช้ต่อไป (Run anyway)** นโยบายของบริษัทอาจซ่อนปุ่ม **เรียกใช้ต่อไป** ในกรณีนี้ให้ใช้ `.bat` หรือขอให้ทีม IT อนุญาตโปรแกรม

**macOS 15 ขึ้นไป:**

1. ดับเบิลคลิก `cresclab-netcheck` เมื่อ macOS แจ้งว่าตรวจสอบโปรแกรมนี้ไม่ได้ ให้ปิดข้อความโดยไม่ย้ายไฟล์ไปที่ถังขยะ
2. เลือก **เมนู Apple** > **การตั้งค่าระบบ** แล้วคลิก **ความเป็นส่วนตัวและความปลอดภัย** ในแถบด้านข้าง (อาจต้องเลื่อนลง)
3. ไปที่ **ความปลอดภัย** แล้วคลิก **เปิด**
4. คลิก **ยืนยันจะเปิด** ปุ่มนี้จะใช้งานได้ประมาณหนึ่งชั่วโมงหลังจากที่คุณพยายามเปิดโปรแกรม
5. ป้อนรหัสผ่านเข้าสู่ระบบ แล้วคลิก **ตกลง** หลังจากนั้น macOS จะจำข้อยกเว้นนี้ไว้ และเปิดโปรแกรมได้ด้วยการดับเบิลคลิก

ขั้นตอนเหล่านี้อ้างอิงจากคู่มือของ Apple
[เปิดแอป Mac จากนักพัฒนาที่ไม่รู้จัก](https://support.apple.com/th-th/guide/mac-help/mh40616/mac)
เจ้าหน้าที่ IT สามารถลบแอตทริบิวต์กักกันใน Terminal ได้ ซึ่งให้ผลเหมือนกัน:

```bash
xattr -d com.apple.quarantine cresclab-netcheck
```

## เนื้อหาในรายงาน

รายงานเป็นไฟล์ข้อความ UTF-8 ที่บันทึกไว้บนเดสก์ท็อป หรือบันทึกไว้ข้างโปรแกรมเมื่อเขียนลงเดสก์ท็อปไม่ได้ การตรวจสอบแต่ละรายการมีเวลาหมดอายุของตัวเอง และการตรวจสอบที่ล้มเหลวหรือค้างจะไม่หยุดรายการอื่น `.exe` จะเขียนผลแต่ละรายการทันทีที่เสร็จ ดังนั้นแม้ปิดหน้าต่างก่อนเสร็จ ผลที่ทำเสร็จแล้วก็ยังอยู่

| ส่วน | สิ่งที่บอกได้ |
| --- | --- |
| Verdict (ต้นรายงาน) | สรุปหนึ่งบรรทัด: โฮสต์ของ Crescendo Lab ตอบกลับทั้งหมด หรือโฮสต์ใดล้มเหลวที่ขั้นตอนใด |
| System, network adapters, DNS, proxy | การตั้งค่าในเครื่อง รวมถึงเซิร์ฟเวอร์ DNS และ proxy หรือสคริปต์ PAC ที่ตั้งค่าเอง |
| Cloudflare trace | IP สาธารณะ และตำแหน่ง Cloudflare ที่ให้บริการลูกค้า |
| แต่ละโฮสต์: DNS, ping, TCP, TLS, HTTPS | แต่ละโฮสต์ของ Crescendo Lab และโฮสต์เปรียบเทียบ `www.cloudflare.com` กับ `www.google.com` ล้มเหลวที่ขั้นตอนใด |
| HTTP port 80 | หน้าบล็อกของไฟร์วอลล์ ซึ่งมักระบุชื่อผู้ผลิตและหมวดหมู่ หน้าที่ยาวจะถูกตัดให้สั้นลง |
| SNI comparison | เครือข่ายกรองตามชื่อโดเมนหรือตาม IP |
| MTU | แพ็กเก็ตขนาดใหญ่ถูกทิ้งระหว่างทางหรือไม่ |
| Repeated HTTPS requests | ความล้มเหลวเกิดเป็นช่วง ๆ หรือไม่ |
| Traceroute | เส้นทางหยุดที่จุดใด |
| Summary (เฉพาะ `.exe`) | หนึ่งบรรทัดต่อโฮสต์ แสดงสถานะ `dns`, `tcp4`, `tcp6`, `tls`, `https` และ `http80` |

### วิธีอ่านรายงาน

1. ดู **Verdict** ก่อน `OK` หมายความว่าโฮสต์ของ Crescendo Lab ตอบกลับผ่าน HTTPS ทั้งหมด โดยนับรหัสสถานะ HTTP ใดก็ได้ว่าเป็นการตอบกลับ `PROBLEM` จะระบุโฮสต์และขั้นตอนที่ล้มเหลว `.exe` จะนับการตอบกลับผ่าน proxy ของระบบด้วย ระบุขั้นตอน (DNS, TCP connect, TLS หรือ HTTPS) และเพิ่มสิ่งที่ SNI comparison แสดง ส่วน `.bat` ตัดสินจากการเชื่อมต่อโดยตรงเท่านั้น หากรายงานยังแสดง "not available yet" แปลว่าโปรแกรมถูกปิดก่อนทำงานเสร็จ
2. **SNI comparison** ช่วยแยกสาเหตุได้เร็วที่สุด:
   - บน `104.18.4.188` มีเพียง `maac.cresclab.com` ที่ล้มเหลว ขณะที่ `www.cloudflare.com` บน IP เดียวกันใช้งานได้: ไฟร์วอลล์ของบริษัทกรองตามชื่อโดเมน ให้ขอทีม IT ของลูกค้าอนุญาต `*.cresclab.com`
   - ทั้งสองชื่อล้มเหลวบน `104.18.x` แต่ใช้งานได้บน `104.16.123.96`: IP หรือเส้นทางถูกบล็อก
   - ล้มเหลวทั้งหมด รวมถึงโฮสต์เปรียบเทียบ: คอมพิวเตอร์เครื่องนี้ใช้อินเทอร์เน็ตไม่ได้ หรือต้องใช้ proxy ที่ยังไม่ได้ตั้งค่า
3. **เวลาของ HTTPS** จะแสดงขั้นตอนที่ไม่ได้เกิดขึ้นด้วย `-` เช่น `tcp=30ms tls=-` หมายความว่าเชื่อมต่อ TCP ได้แล้ว แต่ TLS handshake ค้าง
4. **ผู้ออกใบรับรอง TLS** ที่ไม่ใช่ CA สาธารณะ เช่น CA ของบริษัทเอง หมายความว่าไฟร์วอลล์กำลังดักจับ HTTPS
5. **MTU:** หากมีเพียง `1472` ที่ไม่ตอบกลับ ถือว่าปกติบนสาย PPPoE เช่น ไฟเบอร์ของ HiNet แต่ถ้า ping ปกติใช้งานได้ และ `1300` หรือ `1200` ไม่ตอบกลับด้วย แปลว่าแพ็กเก็ตขนาดใหญ่ถูกทิ้ง
6. **Traceroute และ ping** ที่หมดเวลาทั้งหมด มักหมายความว่าเครือข่ายบล็อก ICMP ไม่ได้แปลว่าเว็บไซต์ล่ม ให้ดูผลของ TCP และ HTTPS แทน

ผลในส่วนสรุปสองแบบนี้เป็นเรื่องปกติและไม่ต้องทำอะไร: `http80` ล้มเหลวบนโฮสต์ `api` และ `cdn` เพราะไม่ได้ให้บริการพอร์ต 80 และ `tcp6=0/2(no-route)` หมายความว่าเครือข่ายไม่มี IPv6 ซึ่งเบราว์เซอร์จะใช้ IPv4 แทน

[ข้อเท็จจริงที่ตรวจสอบแล้ว](docs/verified-facts.md) (ภาษาอังกฤษ) บันทึกพฤติกรรมที่ตรวจสอบไปแล้ว เช่น พฤติกรรมของ CI runner และ Windows Firewall จึงไม่ต้องตรวจสอบซ้ำ

## การพัฒนา

[mise](https://mise.jdx.dev/) กำหนดเวอร์ชันของ Go, golangci-lint และ GoReleaser ไว้ใน `mise.toml` ส่วน `GOTOOLCHAIN=local` ทำให้ Go ไม่ดาวน์โหลด toolchain อื่นเอง

```bash
mise install
mise run check     # lint for every target OS, race-enabled tests, config check
mise run snapshot  # build and package every target into dist/
```

`go run .` จะรันการตรวจสอบบนเครื่องปัจจุบัน โปรแกรมจะรอให้กด Enter ตอนท้าย เพื่อไม่ให้หน้าต่างคอนโซลที่เปิดด้วยการดับเบิลคลิกปิดไปทันที

โฮสต์ที่ตรวจสอบและ IP ของ Cloudflare ที่กำหนดไว้ อยู่ทั้งใน `main.go` และ `scripts/cresclab-netcheck.bat` เมื่อ DNS เปลี่ยน ให้อัปเดตทั้งสองไฟล์พร้อมกัน

## CI และการออกเวอร์ชัน

- **CI** ทำงานในทุก pull request และทุกครั้งที่ push ไปที่ `main`: lint, unit test บน Linux, macOS และ Windows, บิลด์ snapshot ของทุกแพลตฟอร์ม และรันโปรแกรมที่บิลด์แล้วบน Linux, macOS และ Windows บน Windows ทั้ง `.bat` และ `.exe` จะถูกรันอีกครั้งบนเครือข่ายที่ Windows Firewall บล็อก IP ของ Cloudflare ที่ Crescendo Lab ใช้ เพื่อตรวจสอบว่าเส้นทางที่ล้มเหลวทำงานจนจบและรายงานได้ถูกต้อง
- **การออกเวอร์ชัน**ใช้ [Conventional Commits](https://www.conventionalcommits.org/) release-please จะเปิด pull request สำหรับการออกเวอร์ชันค้างไว้บน `main` เมื่อ merge แล้ว จะสร้าง tag และ GitHub release จากนั้น GoReleaser จะอัปโหลดไฟล์บีบอัด, `.bat` แยกต่างหาก และ `checksums.txt` ใน workflow เดียวกัน pull request ที่ release-please เปิดใช้ `GITHUB_TOKEN` จึงไม่ทำให้ CI ทำงาน และแก้ไขเพียง `CHANGELOG.md` กับ manifest ของเวอร์ชันเท่านั้น
- **Dependency:** Dependabot จะเปิด pull request ทุกสัปดาห์สำหรับ Go module และ GitHub Actions ส่วนเวอร์ชันของเครื่องมือใน `mise.toml` ต้องอัปเดตเอง
